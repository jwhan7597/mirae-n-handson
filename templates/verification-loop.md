# AI 검증루프 v1 · 2회차

에듀테크R&D팀(rnd) **실습용 초안**. 실제 사내 표준·팀 합의가 완료된 문서는 아니다.
- 변경 요약1: 작성·리뷰 역할을 분리하고 수용/반박/확인 필요와 재리뷰 기록을 남긴다.
- 변경 요약2: 실제 테스트 결과와 요청 범위를 파일로 검증하고 모호한 판정 문장을 없앴다.
- 변경 요약3: 기준은 approval-checklist.md 한 곳에 두고 verify Skill이 매번 읽는다.

## 역할

| 역할 | 할 일 |
|---|---|
| 작성 세션 | 구현·테스트·리뷰 이슈 판정·수용한 치명/경고 수정. 제안은 목록으로 남김 |
| reviewer Sub-agent | 새 컨텍스트에서 diff·요청·체크리스트 대조. 코드 수정·테스트 실행 금지 |
| tester Sub-agent | 부족한 동작 테스트만 추가하고 변경 폴더의 테스트 실행·실패 분석. 소스·기존 기대값·스냅샷 수정 금지 |
| verify 메인 세션 | 두 완료 보고를 합쳐 최종 판정·보고서 기록. 실제 보고 충돌은 기록하고 사람에게 질문 |
| 사용자 | 요청 범위 확정, 판단이 필요한 쟁점 확인, 실제 머지 결정 |

기본은 작성 Opus/리뷰 Sonnet의 별도 세션이다. 사용량 제약이 있으면 같은 모델의 새 세션도 가능하며 실제 모델을 기록한다.
이번 실습의 작성·대응 역할은 Codex, 독립 리뷰는 새 Sonnet 세션으로 수행했다.
실제 페어·팀원 합의가 없으면 합의했다고 기록하지 않는다.
Day2-4부터 `/verify`가 프로젝트의 두 Sub-agent에 위임한다. 해당 Sub-agent가 없으면 기존 독립 리뷰 세션이 그 역할을 직접 수행한다. `model: inherit`은 호출 세션의 모델을 따른다.

## 절차

1. **요청 확인:** 요청·호환 조건·제외 범위를 확인한다. 없으면 판정하지 말고 먼저 묻는다. 기존 승인이 있는 작업은 반복 승인으로 막지 않는다.
2. **대상 고정:** 비교 기준과 HEAD를 기록하고 변경 파일 목록·diff를 읽는다. patch 요청은 원본 커밋 메시지의 제목·본문·호환 조건을 함께 확인하고 적용 전 git apply --check를 실행한다. 외주사의 자체 정리 설명을 요청자의 범위 승인으로 간주하지 않는다.
3. **기준 적용:** reviewer에게 동일 요청·비교 범위·승인된 준비 작업을 넘긴다. 저장소 루트의 templates/approval-checklist.md, CLAUDE.md, convention-check Skill을 읽어 각 적용 항목을 예/아니오/해당 없음으로 대조하게 한다.
4. **테스트:** tester에게 같은 범위와 테스트 누락 목록을 넘겨 필요한 테스트만 추가하고 변경된 폴더만 실제 실행하게 한다. API는 modern/api의 ./gradlew test, 화면은 modern/web의 npm test, 이관은 characterization의 레거시·새 API 비교를 함께 실행한다. 캐시 여부·실행하지 못한 이유·기존 제외를 기록한다. 메인은 두 완료 보고로 최종 판정한다.
5. **판정:** 체크리스트의 네 기준을 표시한다. 필수 항목의 아니오/확인 필요, 미해결 치명/경고가 있으면 반려한다. 추정·제안과 확정 오류를 구분한다.
6. **이슈 반환:** 작성 세션은 각 이슈를 수용/반박/확인 필요로 나누고 근거를 적는다. 수용한 치명/경고만 수정하고, 필요한 다른 파일이 있으면 기존 승인 범위를 확인한다.
7. **커밋·재리뷰:** 작성 역할이 로컬 커밋한다. 코드가 바뀌면 현재 빌드로 API를 다시 띄운다. 새 리뷰 컨텍스트에서 같은 비교 범위와 기준으로 재검토하여 첫 보고서와 비교한다.
8. **기준 보강:** 실제 판정에서 모호했던 문장을 예/아니오 항목으로 고친다. 이전 사례3개를 새 기준으로 재판정하여 변화 여부를 기록한다.

## 기록

- 마이그레이션: docs/verify/migration-review-1.md, migration-review-response.md, migration-review-2.md.
- 외주 PR: docs/verify/vendor-pr-verdicts.md. PR/판정/미충족 기준/파일:줄 근거/수정 요청을3행으로 남긴다.
- 테스트는 실제 명령·통과/실패/건너뜀 수와 실패 이름만 보고한다. 전체 로그는 별도 증빙에 둔다.
- 외주 검토는 각각 독립 브랜치로 한다. 분리된 worktree도 가능하다. 검토용 patch를 작업 브랜치에 머지하지 않는다.

## 경계

- reviewer는 어떤 파일도 수정하지 않는다. tester는 필요한 테스트 추가만 가능하며 소스·설정·기존 기대값·스냅샷·Git 이력은 수정하지 않는다. verify 메인은 지정된 보고서만 저장한다.
- 적용하지 않은 patch의 테스트는 실행하지 않음으로 남기고 승인 근거로 쓰지 않는다.
- 줄번호 근거가 없는 지적은 확인 필요다. 승인된 준비 작업과 기존 문제를 새 범위 이탈로 세지 않는다.
- 실제 비밀값·더미 인증값의 원문·인코딩값을 보고서에 복사하지 않는다.
- 리뷰어의 추정이 틀리면 코드 근거로 반박한다. 원문 보고서는 보존하고 대응 기록에서 정정한다.
- 최신 기준은 templates/approval-checklist.md다. docs/approval-checklist.md의 기존 v0 복사본을 최신 기준으로 사용하지 않는다.
- 팀 저장소 반영은 Day2-4에서 한다. 이 차시의 결과물은 로컬 Git에 커밋한다.

## 업무 적용

AI가 작성한 문항 검색·배포 기능과 외주 납품 PR의 머지 전 검수에서 동일한 절차를 사용한다.
