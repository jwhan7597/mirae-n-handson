# 승인 체크리스트 v1 · 2회차

에듀테크R&D팀(rnd) **실습용 초안**. 실제 사내 표준·팀 합의가 완료된 문서는 아니다.
- 변경 요약1: 새 동작의 테스트와 실제 실행 결과를 확인하는 항목으로 바꿨다.
- 변경 요약2: 인증값·데이터 손실·권한 우회·외부 입력 SQL 삽입을 구체화했다.
- 변경 요약3: 범위와 컨벤션을 예/아니오로 판단하고 고정 SQL 조각·교육용 더미 예외를 구분했다.

## 판정 방법

각 항목은 예/아니오로 답한다. 적용하지 않는 항목은 근거와 함께 해당 없음으로 표시한다.
필수 항목의 아니오 또는 확인 필요가 하나라도 남으면 반려한다. 제안은 판정에 영향을 주지 않는다.
이번 diff에 없는 기존 문제와 승인된 준비 작업은 새 범위 이탈로 세지 않는다.

## 심각도

- **치명**: 배포 코드의 인증정보 하드코딩·실제 비밀값 노출, 요청하지 않은 데이터 손실, 인증/권한 우회, 외부 입력의 SQL 구문 직접 삽입처럼 근거가 확인된 문제. 1건 이상이면 반려한다.
- **경고**: 새 동작 테스트 누락, 범위 이탈, 계층 규칙·빈 catch·임시 출력 등 필수 항목 위반. 미해결1건 이상이면 반려한다.
- **제안**: 필수 항목을 충족하면서 더 개선할 수 있는 테스트 구성·네이밍·유지보수 의견. 목록으로 남긴다.
- **확인 필요**: 실행·근거가 부족해 확정하지 못한 항목. 필수 항목이면 승인하지 않는다.

실습 patch의 인증값은 더미라고 명시하고 원문·인코딩값을 보고서에 복사하지 않는다.
더미여도 배포 코드가 인증정보를 하드코딩해 요청에 사용하는 패턴이면 실습에서 반려한다. 실제 유출 사고가 있었다고 주장하지 않는다.
테스트용 가짜 인증값이 테스트에만 격리되어 실제 자격증명으로 쓰이지 않는 경우는 비밀 유출로 단정하지 않는다.

## 1. 테스트 통과

- [ ] 변경된 폴더의 테스트 명령을 실제로 실행하고 이번 실행의 종료 상태·통과/실패/건너뜀 수를 기록했는가?
- [ ] 실행한 검사에서 실패·오류가0건인가?
- [ ] 새 public 동작·추가 분기·경계에 대응하는 테스트가 있는가? 단순 getter/setter/생성자와 DTO 접근자는 제외한다.
- [ ] 새 동작 테스트가 요구한 결과를 검증하는가? 기존 테스트 통과만으로 새 동작의 검증을 대신하지 않았는가?
- [ ] 기존 테스트·스냅샷을 삭제·완화하거나 새 skip/@Disabled로 실패를 숨기지 않았는가?
- [ ] 레거시 이관이면 같은 테스트를 레거시와 새 API 양쪽에 실행해 결과가 같은가?
- [ ] 뷰·스키마를 변경했으면 테스트용 복사본·fixture도 대응하는지 확인했는가?

기존 예시의 레거시 전용 skip처럼 변경 전부터 존재하고 적용 범위가 명시된 제외는 수와 이유를 기록한다.
새 동작 없이 문서·주석만 바뀐 경우 새 테스트 추가 항목은 해당 없음이다.

## 2. 치명 이슈 0건

- [ ] 배포 코드·설정에 실제 비밀번호·토큰·키 또는 외부 요청에 쓰는 하드코딩 인증정보가 추가되지 않았는가?
- [ ] 외부 입력 값은 바인딩되고 SQL 구문·식별자·정렬 방향에 직접 이어 붙이지 않았는가?
- [ ] 동적 정렬·고정 SQL 조각의 선택이 enum/고정 allowlist로 제한되는가?
- [ ] 데이터 삭제·덮어쓰기·권한 변경이 있으면 요청에 명시되어 있고 관련 실패·경계가 검증되는가?
- [ ] 이번 변경으로 인증·권한 검사를 우회하는 경로가 생기지 않았는가?

고정 SQL 리터럴을 조합하고 값을 바인딩하는 방식은 SQL 인젝션으로 단정하지 않는다.
입력 검증 추가가 요청에 없는 레거시 동작을 바꾸면 보존 계약에 따라 판정한다.

## 3. 요청 범위 이탈 없음

- [ ] 요청 범위·호환 조건·제외 범위가 한 문장 또는 승인된 작업 기록으로 확인되는가?
- [ ] 변경된 각 파일이 그 요청이나 승인된 준비 작업으로 설명되는가?
- [ ] 요청에 포함되지 않은 파일·기능 변경이 없는가? 필요한 import 정리는 요청 대상 파일 안에서만 허용한다.
- [ ] 의존성·DB 스키마/시드·접속 설정 변경이 있으면 요청 또는 기존 승인에 포함되는가?
- [ ] 비밀값·회사 내부 데이터·환경 파일이 커밋 대상에 추가되지 않았는가?

## 4. 컨벤션 준수

- [ ] 저장소 루트 CLAUDE.md와 convention-check Skill의 적용 항목을 실제 diff에 대조했는가?
- [ ] 컨트롤러가 Repository/JdbcTemplate/SQL을 직접 호출하지 않고 Service를 거치는가?
- [ ] 응답 DTO와 생성자 주입 등 기존 계층 규칙을 지켰는가?
- [ ] 예외를 빈 catch로 삼키거나 오류를 성공으로 숨기는 코드가 추가되지 않았는가?
- [ ] 임시 System.out/printStackTrace/console.log 또는 사유 없는 검사 무시가 추가되지 않았는가?
- [ ] 명시된 레거시 호환 동작과 기존 오류 처리 규약을 적용 범위에 맞게 유지했는가?

동작에 영향 없는 네이밍 취향은 제안으로 기록한다. 근거가 없는 컨벤션 지적은 확인 필요로 남긴다.

## 출력

첫 줄: 판정(승인/반려). 이어 네 기준의 결과·근거 표, 이슈 목록을 적는다.
이슈는 심각도·파일:줄번호·근거·수정 방향을 모두 적고, 테스트 결과는 요약만 남긴다.
판정은 리뷰 결과이며 실제 머지 결정은 사용자가 한다. 리뷰어는 코드를 고치지 않는다.
