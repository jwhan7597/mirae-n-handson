# RCA: b-deploy-5xx (부분 실행: 1절·2절·3절 가설 표까지)

대상: `incident-logs/b-deploy-5xx` (교육용 더미 로그). 시각은 모두 KST.

**요약 (부분 실행 기준)**
- 5xx는 두 종류다. 13:41:51~13:41:59의 502 8건과, 09:52부터 간헐적으로 나타나다 13:46:38 이후 늘어난 500이다.
- 502 8건은 v1.4.2 단일 호스트 재기동 구간과 겹친다. 이것은 상관 관계이고 원인은 확정하지 않았다.
- 500은 배포 전 7건, 배포 후 39건이다. 모두 Assignment id 9 미존재 예외이고 `redistribute` 또는 단건 조회 경로에서 났다.
- 단일 원인은 확정하지 않았다. 가설 4개를 세웠고 검증·코드 대조·원인·수정안(4절 이후)은 실행하지 않았다.

## 1. 수집 범위

| 파일 | 줄 수 | 기간 | 시각 형식 |
|---|---|---|---|
| `nginx-access.log` | 20,365 | 09:00:00~14:39:58 | `+0900` 명시 |
| `app.log` | 2,938 | 09:00:04~14:39:57 | `+09:00` 명시 |
| `deploy-history.md` | 39 | 배포표 (2026-09-17 외 3건) | 문서에 "모두 KST" 명시 (`deploy-history.md:3`) |

- 기간은 2026-09-17 약 5시간 40분이다. 타임존은 세 파일 모두 KST(+09:00)로 표기되어 있어 별도 가정이 필요 없다.
- 스택 트레이스 줄은 같은 예외에 속한 줄이다. 예외 한 건을 요청 한 건으로 세지 않았다.
- 평소 상태: 09:00~13:40에 요청 16,728건, 500은 7건(약 0.04%), 502는 0건이다. 409(마감 과제 재배포)는 31건으로 평소에도 있다.
- 평소와 다른 구간 (이 구간만 읽었다):
  - A. 09:52 (첫 5xx, 분당 500 3건)
  - B. 10:31 (500 1건)
  - C. 11:17~11:18 (500 3건)
  - D. 13:38~13:46 (배포 및 502 8건)
  - E. 13:46~14:35 (500 39건, 분당 1~4건)
- 앞뒤 여유: 09:00~09:50은 5xx가 없고(WARN 409만), 14:35~14:39:58은 500이 없다. 로그가 14:39:58에 끝나 회복 여부는 5분만 볼 수 있다.
- 구간별 건수 (도구 `counts` 결과):

- 13:38~13:46 구간은 요청 535건 중 502가 8건이다.
- 404는 두 구간 모두 비슷한 비율로 계속 나오고 5xx 시점과 맞지 않아 분석에서 제외했다. 이유는 코드로 확인하지 않았다.
- 로그로 확인할 수 없는 것: nginx error 로그와 upstream 정보가 없다. DB 로그와 `api-2` 로그도 없다.

## 3. 가설과 검증 (가설 표까지)

단일 원인은 확정하지 않는다. 아래는 서로 다른 계층의 후보이다. 상태 열은 모두 `미검증`이다.

| # | 계층 | 가설 | 지지 근거 (관찰) | 반증 조건 | 확인 방법 | 상태 |
|---|---|---|---|---|---|---|
| H1 | 코드·배포 | v1.4.2가 재배포 응답에 `listByClass`를 추가해, 재배포 뒤 이력 조회에서 새 500 경로가 생겼다 | 배포 후 500 39건의 호출 지점이 `listByClass`·`redistribute`다 (`app.log:1286`, `app.log:1294`). 변경 요약과 일치 (`deploy-history.md:15-16`). 배포 후 `redistribute` 48건 중 500이 39건이다 | `listByClass`를 거치지 않는 경로(단건 조회)에서도 같은 데이터로 500이 난다면 이 가설만으로는 설명이 안 된다. 배포 전에 이미 `listByClass` 경로가 호출되고 500이 났다면 새 경로가 아니다 | `DistributionController.java`, `DistributionService.java` 코드 대조 (4절). 배포 전 호출 지점 `app.log:205`, `app.log:463`과 비교 | 미검증 |
| H2 | 데이터 | Assignment id 9가 DB에 없는 채로 남아 있어(참조 무결성 깨짐), 이 행을 읽는 모든 경로가 500이 된다. 배포가 원인이 아니라 기존 결함이 드러난 것일 수 있다 | 배포 전 구간에서도 같은 예외가 3개 구간에 있다 (`app.log:195`, `app.log:452`, `app.log:656`). 배포 후 메시지도 같은 id 9다 (`app.log:1276`). `redistribute`와 단건 조회에서 모두 났다 | DB에 Assignment id 9가 정상 존재하면 기각. 배포 후 42·43이 id 9와 무관한 학급인데도 같은 id를 가리킨다면 연결을 따로 설명해야 한다 | 읽기 전용 확인: 스테이징 또는 복제본에서 `assignment` id 9 조회, distribution 41·42·43의 assignment·class 컬럼 조회. 운영 DB 접속은 하지 않는다 | 미검증 |

- 가설 간 관계: H1과 H2는 함께 성립할 수 있다. 예를 들어 id 9 결함이 원래 있었고, v1.4.2가 그것을 건드리는 경로를 늘렸을 수 있다. 이 문장은 추정이다.
- 배포 후 500의 호출 지점이 바뀐 것은 사실이다. 배포 전은 `loadOrThrow`(`:65`)이고 배포 후는 `listByClass`(`:38`)다. 같은 예외 메시지가 반복된다는 것도 사실이다. 이것만으로 원인을 정하지 않는다.
- 배포 직후에 시작된 것처럼 보이는 500은 상관 관계다. 배포 전에도 같은 예외가 있었다(09:52, 10:31, 11:17~11:18). 11:17~11:18은 배포보다 약 2시간 22~23분 전이다.

## 미실행 범위

- 로그 반증 시도, 코드·설정 대조, 가설 유지/기각 판정, 4절 원인·5절 근거 로그 줄 정리·6절 수정안·7절 재발 방지·8절 모니터링·9절 확인하지 못한 것은 이번 지시 범위 밖이라 실행하지 않았다.
- 원본 로그·소스·설정·기존 보고서는 수정하지 않았다. 커밋·푸시도 하지 않았다.

## 마스킹 적용

기준: 이 보고서 본문에 실제로 남은 마스킹 표기 수이다. 선택 구간의 도구 출력 단계에서 이미 변환된 값은 변환 후 표기만 센다. 별칭 대응표는 파일에 남기지 않았다.

- IP 주소: 0건 (발췌에서 클라이언트 IP를 생략했다)
- 이메일: 1건 (`deploy-history.md:21` 발췌의 마스킹된 승인자 표기)
- 학생 식별자: 0건 (발췌에 쓰지 않음)
- 토큰·세션 ID·API 키·Authorization 값: 0건 (인용하지 않음)
- 비밀번호·접속 문자열: 0건

잔존 검사 결과는 응답에 별도로 보고한다.

작성 역할의 원문 대조: 발췌·시간 차이·표 표시를 Codex가 정정했다. 최초 재사용 결과는 마스킹된 증빙으로 보존했다. 원인 판정과 코드 대조는 추가하지 않았다.
